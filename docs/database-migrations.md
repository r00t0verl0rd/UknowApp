# Совместимость БД и автоматические обновления (ветка test)

Core поддерживает SQLite (по умолчанию) и PostgreSQL. При запуске, включая запуск после восстановления резервной копии, вызывается initialize_database(). Ручной промежуточный запуск каждой старой версии не нужен для проверенных схем.

## Обновление

1. Сделайте проверенную резервную копию БД, архива файлов, VAPID-ключей и постоянных томов коннекторов/брокера. Для SQLite используйте штатный полный ZIP из админ-панели; для PostgreSQL — pg_dump/pg_restore и отдельную копию каталога data.
2. Обновите приложение в ветке test и выполните docker compose up -d --build. Не удаляйте тома и не запускайте две версии Core одновременно на одной БД.
3. Проверьте health, логи, пользователей, переписки, привязки, вложения и уведомления.

Миграции запускаются до HTTP API, NATS и коннекторов. SQLite использует BEGIN IMMEDIATE, PostgreSQL — транзакционную advisory lock. Изменения схемы и отметки schema_migrations сохраняются в одной транзакции; при ошибке откатываются. После всех шагов проверяются таблицы и колонки актуальных моделей. Повторный старт не выполняет уже отмеченные шаги. В случае неполной или неизвестной схемы запуск останавливается с ошибкой, а при штатном restore возвращаются исходные данные. Проверка структуры не гарантирует корректности произвольной сторонней или повреждённой БД.

## Политика разработки

Каждое изменение схемы получает явную миграцию с уникальным идентификатором; новые шаги добавляются в MIGRATIONS. Исторические идентификаторы не меняются и не удаляются. Единственный источник миграций — реестр MIGRATIONS в `backend/app/migrations/__init__.py` и его помощники. Дублирующие ревизии Alembic удалены из дерева проекта; история доступна в Git. Библиотека Alembic остаётся зависимостью для DDL-операций внутри штатных миграций, но не запускает отдельный реестр. Существующая таблица `alembic_version` не используется и не удаляется. Для существующей старой БД сначала выполните штатное обновление на копии.

Запрещено заменять рабочую БД пустой при обновлении. Не угадывайте преобразования неизвестных колонок. Сначала переносите бизнес-данные и идентификаторы, затем удаляйте устаревшие структуры. Известные исключения: ранее снятый модуль интерактивных досок, техническое состояние старой панели бота и истёкшие сессии/коды. Откат на старый код после удаления колонок требует восстановления резервной копии.

## Регрессионные проверки

backend/tests/fixtures/schema_*.py — замороженные исторические схемы из коммитов репозитория, только для тестов. Проверяются переходы со встроенного Telegram, раннего WebSocket Gateway, ранней одноадресной доставки NATS и версии до многодевайсного Push. Тесты проверяют перенос пользователей и паролей, назначений, обычных и личных диалогов, метаданных вложений, прочтения, внешних ID, привязок, очередей и подписок, повторный запуск и SQLite rollback при искусственной ошибке. Database compatibility CI запускается в test для SQLite и PostgreSQL. Физические архивы рабочих серверов в тестах не используются.

## Восстановление

SQLite поддерживает полный ZIP и восстановление отдельной БД при наличии всех медиафайлов. Новая версия запускает те же миграции после установки старой БД из архива. При ошибке запуска штатный restore возвращает предыдущие данные. PostgreSQL не поддерживает SQLite ZIP/импорт через веб-API (HTTP 501). Перенос между SQLite и PostgreSQL не автоматизирован, смена DATABASE_URL не переносит данные. Сохраняйте исходные медиафайлы и VAPID-ключи отдельно от SQL-дампа. Состояние NATS и коннекторов должно соответствовать восстановленной БД; подробности — bots-gateway.md.
