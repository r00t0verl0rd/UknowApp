# Хранение данных, PostgreSQL и Alembic

## Цель и границы

- Бизнес-данные описываются SQLAlchemy-моделями в `backend/app/models.py`.
- Конкретная СУБД задаётся `DATABASE_URL` (SQLite по умолчанию, PostgreSQL через `psycopg`).
- Размер БД и провайдер-зависимые технические операции вынесены в отдельный модуль.
- Полный ZIP, экспорт и восстановление SQLite **не поддерживаются** при подключённом PostgreSQL.
  Они возвращают HTTP 501; используйте проверенный `pg_dump`/`pg_restore` и отдельную копию каталога `data`.
- Перенос записей между SQLite и PostgreSQL **не автоматизирован**. Простая смена URL создаст
  новое/пустое подключение, а не перенесёт пользователей и сообщения.

## Текущая переходная совместимость

Стартовый код предыдущих выпусков вызывает `initialize_database()` (создание отсутствующих
таблиц и выполнение старых одноразовых миграций). Он оставлен для безопасного обновления
существующих серверов. **Это не полноценный Alembic-only режим**. Новые изменения схемы
должны оформляться отдельными проверенными ревизиями Alembic, а не новой автоматической
логикой в `initialize_database()`. Удалять совместимость следует только отдельной проверенной
миграцией развёртывания.

## Проверенная начальная ревизия

`20261123_01` — защитная базовая ревизия. Она создаёт отсутствующие таблицы из текущих
SQLAlchemy-моделей, не удаляя существующие записи или таблицы. Она **не изменяет существующие
столбцы**, поэтому для старой базы перед её применением нужно удостовериться, что все прежние
миграции уже выполнены. Не используйте подход `create_all()` в следующих ревизиях:
каждую новую операцию следует явно фиксировать через `op.create_table`, `op.add_column` и т. д.
Откат базовой ревизии намеренно запрещён.

Для действующей SQLite-базы:

1. Сделайте полную резервную копию в админ-панели и проверьте восстановление на тестовой копии.
2. Запустите обновлённую версию приложения, убедитесь в работоспособности.
3. На тестовой копии выполните `alembic upgrade head`, просмотрите `alembic current` и `alembic check`.
4. Только после этого вручную выполните на основном сервере:

```bash
docker compose exec backend alembic -c /app/alembic.ini upgrade head
docker compose exec backend alembic -c /app/alembic.ini current
```

## Ручной процесс каждой следующей миграции

1. Снять резервную копию и проверить возможность восстановления.
2. На копии базы получить черновик:

```bash
alembic -c alembic.ini revision --autogenerate -m "описание изменения"
```

3. **Вручную прочитать весь файл** ревизии. Проверить `DROP`/`ALTER`, переименования,
   типы полей, внешние ключи, индексы, значения по умолчанию и перенос существующих данных.
   Alembic не всегда распознаёт переименования и не гарантирует безопасных преобразований.
4. Проверить и прогнать миграцию сначала на копии SQLite и PostgreSQL, отдельно проверить
   пользовательские функции, диалоги, резервное копирование и целостность данных.
5. Утвердить ревизию в код-ревью и только затем явно выполнить `upgrade head` на сервере.

**Запуск веб-сервера не должен автоматически выполнять новые ревизии Alembic.**
Не делайте `alembic upgrade head` частью Docker `CMD` или startup-hook.

## PostgreSQL: резервные копии

Ни `pg_dump`, ни SQL-дампы не включают файлы из каталога `data`. Сохраняйте и
проверяйте **обе части** — базу и медиакаталог / VAPID-ключи.
Не используйте полные ZIP-архивы SQLite для восстановления PostgreSQL.
