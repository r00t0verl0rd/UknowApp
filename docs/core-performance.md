# Core: производительность и отзывчивость (test)

Core и веб-API имеют приоритет над внешней доставкой. NATS один, его недоступность не останавливает веб.

## Обязательное правило SQL

Запрещено выполнять синхронные операции SQLAlchemy (включая получение соединения, lazy load, транзакции) непосредственно внутри async def на event loop. Синхронные HTTP endpoints объявляются def, FastAPI выполняет их в threadpool. Для асинхронного NATS Gateway используется run_db: выделенный пул с одним слотом для последовательных операций и одним для независимых чтений, отдельная ORM-сессия внутри каждой операции. Не передавать ORM-объекты в event loop. В SSE проверка прав и replay выполняются в потоках с локальными сессиями. Startup миграций и restore вынесен в поток. Завершение выполняющейся транзакции не бросается при отмене задачи. Уведомление SQL outbox потокобезопасно.

CI: статическая проверка прямых синхронных вызовов в async def и runtime-проверка SQLAlchemy в backend-тестах. Медленный SQL Gateway моделируется отдельным подключением; HTTP health должен завершиться до освобождения SQL. Записи шлюза выполняются последовательно. Статистика очереди и поиск адресатов обновления панели используют отдельный слот чтения. Это не гарантия абсолютного приоритета в самом движке: SQLite всё ещё сериализует записи, PostgreSQL может ждать блокировок. Настоящие нагрузочные замеры на VPS обязательны для количественной оценки.

## Изменения горячих путей

- Подтверждение доставки не пересчитывает счётчики и превью диалога. Frontend не инициирует полное восстановление inbox из-за отсутствия summary у delivery; администратор получает изменённые метаданные доставки в SSE, участники не получают внешние статусы.
- Отметка прочтения выполняется атомарным UPDATE отдельного поля teacher_read_at/student_read_at, без перезаписи JSON; проверка отсутствия непрочитанных не создаёт ненужную запись.
- SQLite резервирует транзакцию перед чтением изменяемого состояния отправки/удаления; PostgreSQL блокирует строки заданий. Это сохраняет корректность поздних подтверждений при удалении сообщения.
- Диагностические результаты Push записываются небольшими пакетами до 16 завершённых результатов, без ожидания сети внутри транзакции. Рассылка на все устройства остаётся независимой.
- Составные индексы очередей и подписок добавляются автоматически миграцией 20261126_06. Исторические схемы проверяются SQLite/PostgreSQL CI. Метрики очередей обновляются раз в 60 секунд вместо 30.

Остаются отдельные задачи: измерение p50/p95/p99 запросов, RAM/CPU/IO на одинаковых данных и ресурсах, контроль общего размера фоновых очередей и безопасная политика хранения технических журналов. Без данных замеров не заявляем проценты ускорения.

## Main DB и Runtime DB

Производительность является обязательным критерием: избегаем повторного чтения, промежуточные вычисления — код/RAM, персистентное техническое состояние — Runtime. Main сохраняет только данные школы и минимальные гарантии целостности. Подробности: runtime-storage.md. PubAck пакетируется, ожидание пустой очереди не выполняет Main SQL до очередного сигнала или сверки.

## SSE и бюджет SQL-запросов

Журнал SSE ограничен RAM: один replay hint до 4 КиБ, очередь подписчика — 128. Публикация и replay не обращаются к SQL. Миграция `20261126_07` удаляет только `realtime_events`, не историю сообщений. Потеря курсора, рестарт или переполнение вызывают полную синхронизацию. Core работает одним процессом; для нескольких нужен общий транспорт событий. Права и видимость диалогов проверяются в Main DB.

Сессия проверяется одним SELECT с JOIN; `/panel/me` использует эту идентификацию. История загружает отправителя через JOIN, без отдельных запросов к аккаунтам мессенджеров.

| --- | ---: |
| 100 сообщений в чате преподавателя | До 4 |

## Счётчики диалогов и курсоры прочтения (20261126_08)

Миграция заполняет `message_count`, `last_message_id`, `last_read_id` учителя и ученика и точные счётчики непрочитанных (teacher/student/admin). Курсор — последнее существующее сообщение непрерывного прочитанного префикса, а не максимальный ID отдельной отметки. Разрозненные прочтения видимых страниц сохраняются.

Запросы непрочитанных используют индексированные генерируемые колонки, курсор и точные условия роли. `mark_read` атомарно обновляет метаданные без извлечения JSON в фильтре. Счётчики и превью читаются одним JOIN без сканирования истории; обновляются транзакционно при вставке, удалении и прочтении, включая bulk SQL.

В SQLite генерируемые поля виртуальные, в PostgreSQL — хранимые. Вместо повторных сканирований истории выполняется короткое индексированное обновление родительской записи. Для восстанавливаемого Runtime используется WAL `synchronous=NORMAL`. 

## Отметки прочтения и события доставки (20261126_09)

Миграция 09 превращает генерируемые колонки версии 08 в записываемые скалярные отметки времени, один раз переносит оба старых JSON-ключа и транзакционно перестраивает индексы и счётчики. В SQLite при прочтении меняется нужная колонка (затронутые страницы всё равно записываются в WAL).

Точные инкрементальные счётчики позволяют получать list/sync за O(число чатов), независимо от объёма истории и количества непрочитанных. Фильтры используют курсор, индексированный признак непрочтения и видимые ID. API сохраняет прежний JSON-формат отметок.

Внешние события доставки получает только администратор, вместе с обновлённым реестром доставки; нет проверки прав участника SSE или полной синхронизации на каждую доставку. Пересекающаяся по времени синхронизация администратора может потребовать сверки. Для старых клиентов/серверов и reconnect остаётся fallback. Личные чаты используют независимые транзакционные счётчики администратора и участника, индекс последнего сообщения и частичные индексы непрочитанных. Список получает участника и счётчики одним SELECT; после записи используются свежие скалярные значения. История по умолчанию ограничена 100 сообщениями. При конфликте ответа о прочтении и SSE/HTTP выполняется адресная сверка активного чата, а не безусловный сброс счётчика.

Тесты проверяют отсутствие записи JSON при прочтении, переход с 08, фильтрацию прав и отсутствие агрегации истории даже при 100 тыс. сообщений.

## Ограничение конкуренции SQLite при чтении чатов

Диагностика на 4 vCPU с 100 параллельными запросами показала 76 запросов истории/с при 40 потоках AnyIO и 154 при 4 (прежний диагностический эксперимент с глобальным лимитом). В рабочем коде ограничивается только число одновременно обрабатываемых запросов списка, истории, сводки, sync/read учебных и личных чатов и коротких SQL-проверок SSE. Ожидание происходит асинхронно до авторизации и открытия сессии, слот освобождается после завершения маршрута; SSE не занимает слот между событиями. Отправка сообщений, вложения, скачивание файлов и прочие API не получают этот лимит. PostgreSQL не ограничивается. WAL, транзакции, проверки прав и формат API не меняются. Для страниц истории и SSE JOIN отправителя загружает только ID и имя вместо всех полей пользователя.

Переменные Core: UKNOWAPP_SQLITE_CHAT_READ_CONCURRENCY (4 по умолчанию, 0 отключает), UKNOWAPP_SQLITE_POOL_SIZE (5), UKNOWAPP_SQLITE_POOL_OVERFLOW (10). Пул сохраняет прежние значения до измерений на VPS; настройки не применяются к in-memory SQLite или PostgreSQL. Не увеличивайте пул вслепую: конкуренция Python/SQLite при большом числе потоков может снизить скорость. Сравнительный CI benchmark проверяет 0 и 4 на одинаковой конфигурации, не подключается к рабочей БД и не отправляет сообщения в мессенджеры. Результаты CI не гарантируют производительность VPS.
