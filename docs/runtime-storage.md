# Main DB / Runtime DB (test)

## Main DB — данные школы

Main DB: школьные данные, авторизация, назначения, диалоги, переписка, привязки, медиаметаданные. Файлы — data/media. Минимальные атомарные намерения доставки/удаления, fencing внешней попытки и конечный результат остаются вместе с бизнес-данными: потеря Runtime не должна повторно отправлять сообщения или лишать возможности удалять внешние копии. BotEventReceipt обеспечивает транзакционную дедупликацию, SSE — ограниченный RAM-журнал, восстанавливается из бизнес-данных при reconnect.

## Runtime DB — техническое состояние

Runtime DB: `data/runtime/runtime.db`, отдельный SQLite Engine и WAL. push_subscriptions (включая результаты), transport_jobs (проекция очереди, состояние публикации, broker_seq, время публикации). Main DB не обновляется при каждом PubAck или проверке retained stream. При пустой очереди Main DB не читается; проекция обновляется по сигналу нового события и сверяется раз в 60 секунд. Диагностика Gateway по-прежнему использует периодическую выборку durable intent. RAM: heartbeat, счётчики, пробуждения, ограниченная очередь Push. NATS — транспорт. Connector — собственный durable spool. Новых контейнеров нет.

## Web Push

Чтение подписок и проверка только актуальных сессий целевых получателей вне HTTP; максимум 128 ожидающих/активных рассылок, при переполнении пропускается уведомление, но не сообщение. Legacy-подписки без сессии сохраняются, но требуют открытия приложения. Выход отзывает сессию независимо от Runtime.

## Миграция и резервные копии

Автоматический split после исторических миграций: запись в Runtime фиксируется до удаления исходной таблицы push_subscriptions и столбцов published_at/broker_seq. Повтор безопасен по endpoint/job id. Runtime недоступна — источник не удаляется, Core работает, монитор повторяет инициализацию. Full ZIP включает SQLite snapshot Runtime; импорт только Main DB сбрасывает Runtime, чтобы не использовать подписки другого снимка. Для точного восстановления остановить внешние отправки и сохранить Main, Runtime, медиа, VAPID и тома NATS/коннекторов вместе. Снимки двух БД не являются одной point-in-time транзакцией. PostgreSQL — отдельный pg_dump и Runtime snapshot.

## Правила производительности

Избегайте polling Main DB в idle, SQL-запросов в event loop, повторных SQL по одному событию. Использовать RAM для вычислимых временных данных, пакеты для записи технических результатов. Нельзя заменять актуальную авторизацию устаревшим кэшем. Тесты проверяют отсутствие Main SQL при пустой транспортной выборке, физический split, восстановление projection и доступность веб-записи при Runtime outage. Количественное ускорение требует нагрузочного теста.

## Публикация в NATS

PubAck обрабатывается в RAM до конца ограниченного пакета (до 50 заданий), затем фиксируется одной транзакцией Runtime. broker_seq уже включён в выборку очереди: отдельный SELECT по каждому заданию не требуется. При падении до фиксации возможна повторная публикация, но Main claim и durable spool исключают повторную разрешённую внешнюю попытку.

## SSE

Миграция 20261126_07 удаляет старую техническую таблицу realtime_events. При перезапуске или потере курсора клиент перечитывает актуальные данные, при сохранённом последнем курсоре воспроизводится один доступный hint. Не требуется писать событие в БД после каждого школьного сообщения.
