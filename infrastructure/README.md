# UknowApp — автоматизация развёртывания двух VPS

Версия комплекта: 0.1.0. Целевая версия UknowApp: `588dc99079f0fc7449f80f621856ac42904c8639`.

Комплект воспроизводит конфигурацию, собранную вручную в ноябре 2026 года. Это **не проверенный на реальных VPS инсталлятор**: проверены синтаксис Bash, встроенный Python и локальный сценарий управляющего скрипта с подменённым SSH. Перед использованием на рабочей школе сначала проверьте на тестовых VPS. Данные и работающие контейнеры не удаляются; существующие неизвестные конфигурации не перезаписываются. Сбой может оставить частично подготовленную систему.

## Файлы

- `deploy.sh` — запускается на Mac/Linux, подключается к двум VPS по SSH, обменивается публичными ключами и выполняет шаги в нужном порядке.
- `server.sh` — выполняет отдельные операции на VPS, автоматически копируется на время запуска; отдельно запускать не нужно.

## Требования и ограничения

- Два выделенных VPS на Debian 13 amd64, прямой SSH-доступ `root` на TCP 22 (пароль или SSH-ключ), systemd. Telegram VPS не должен обслуживать другие приложения/публичные порты. Сверьте отпечатки SSH-хостов. Рекомендуется ключевая авторизация и ограничение root SSH после установки.
- У основного сервера должен быть публичный IPv4, который виден Telegram VPS как источник пакетов WireGuard. На внешнем firewall провайдера разрешите TCP 22 и UDP 51820 (на Telegram VPS только от main), а на основном VPS — TCP 80/443 и UDP 443 при необходимости HTTP/3. Порты 8081, 2049 и RPC в интернет не открывайте.
- Для версии проекта из комплекта домен в `frontend/Caddyfile` зафиксирован: `uknowschool.ru` и `www.uknowschool.ru`. Для новой установки настройте DNS/HTTPS самостоятельно. Другой домен требует изменения Caddyfile и новой версии скрипта. Основной firewall и DNS скрипт не меняет.
- Существующий Git-репозиторий должен находиться в `/home/uknow/UknowApp` или `/home/uknowbot/UknowApp`, соответствовать указанному коммиту и не иметь изменённых отслеживаемых файлов. Для нового репозитория проверенный коммит будет загружен автоматически. Обновление версии приложения не входит в задачу.
- На основном VPS сохраняется существующая `.env` и база. На новом VPS создаётся SQLite-конфигурация из шаблона. Уже работающий PostgreSQL не мигрируется. Миграция локального API с другого endpoint и нестандартная конфигурация сетей не поддерживаются.
- Для Telegram API нужны API ID/Hash с my.telegram.org/apps. Токен BotFather используется на основном VPS. Для новой установки ввод паролей скрыт; скрипт не печатает токен, Hash или приватные ключи. Не запускайте скрипты с `bash -x`. Пользователи в группе `docker` имеют фактически привилегии root, хотя процесс Telegram API работает с UID/GID 101.
- Новая установка фиксирует digest образа Telegram Bot API, использованного при ручном развёртывании. Существующий `.env` с `latest` остаётся без изменений; имеющийся образ не обновляется автоматически. Обновлять образы и систему безопасности нужно отдельным процессом.

## Запуск с компьютера

На компьютере клонируйте репозиторий и перейдите в папку установщика:

```bash
git clone https://github.com/r00t0verl0rd/UknowApp.git
cd UknowApp/infrastructure
```

Выполните:

```bash
bash deploy.sh 192.0.2.10 198.51.100.20
```

Это условные адреса из документационных диапазонов TEST-NET. Подставьте реальные публичные IPv4 ваших VPS: первый — основной, второй — Telegram. Публичные IP не зашиты в скриптах; из аргументов формируются endpoint WireGuard и ограничения firewall. Внутренняя подсеть WireGuard 10.77.0.0/24 фиксирована, её пересечение с существующими маршрутами проверяется. Если меняется IP уже настроенного VPS, скрипт намеренно не перезапишет отличающиеся конфигурации WireGuard/firewall: их нужно отдельно согласованно обновить. Для новых чистых VPS достаточно передать новые адреса. Скрипт использует стандартную проверку SSH host key и открывает SSH-соединения к обеим машинам; при необходимости спросит пароль. Для проверки нового подключения после firewall возможен ещё один запрос пароля. На вопрос о подготовке введите `PREPARE`. Если файлов `.env` нет, скрипт предложит ввести API ID/Hash, пароль администратора и токен. Перед остановкой действующего cloud backend нужно отдельно ввести `MIGRATE`. Убедитесь, что других процессов polling с тем же токеном нет.

Для действующей инфраструктуры, уже настроенной вручную, повторная установка обычно **не нужна**. Сначала используйте проверку:

```bash
bash deploy.sh 192.0.2.10 198.51.100.20 --check
```

Она понимает существующий тестовый файл `.nfs-test` из ручной установки. При отсутствии обоих тестовых файлов или необходимых конфигураций проверка остановится.

Только подготовка инфраструктуры, без остановки cloud backend и без вызова `logOut`:

```bash
bash deploy.sh 192.0.2.10 198.51.100.20 --prepare-only
```

При необходимости повторите без `--prepare-only`. Если приложение уже работает в нужном local-режиме, cloud logout повторно не вызывается. Скрипт прекращает работу при отличающихся существующих конфигурациях; это сделано намеренно, чтобы не уничтожить настройки других служб.

## Что создаётся

| Служба | Основной VPS | Telegram VPS |
|---|---|---|
| Linux-пользователь | `uknow` | `uknowbot` |
| WireGuard | `10.77.0.1/24` | `10.77.0.2/24`, UDP 51820 |
| Docker | backend / frontend | только `compose.telegram.yml` |
| Telegram API | `http://10.77.0.2:8081` | bind на приватный IP |
| NFS | `/srv/uknow-telegram-remote` (ro) | `/srv/uknow-telegram`, NFSv4, UID/GID 101 |
| Firewall | существующий не меняется | отдельная таблица `inet uknow_guard`, публичный SSH, WG от main |
| Автозапуск | Docker ждёт попытку NFS; `nofail` | Docker и NFS после WG и firewall |

Firewall на Telegram VPS применяется с таймером отката на 5 минут при первичной установке, затем проверяется новым SSH-соединением и закрепляется. Существующие отдельные таблицы Docker не очищаются. NFS экспортируется только главному IP в режиме чтения с `all_squash` (101:101). Добавляются записи systemd и fstab; существующий файл fstab сохраняется перед добавлением строки. Не копируйте приватные ключи между VPS.

## Переключение и резервные копии

Скрипт создаёт резервную копию `.env` в `/root/uknow-backup-...` до остановки cloud backend. Это **не резервная копия базы, медиа или всего VPS**. На рабочем проекте заранее скачайте полный ZIP через админку; для PostgreSQL потребуется отдельная процедура. Скрипт не выполняет `docker compose down -v` и не меняет `DATABASE_URL`.

После остановки backend токен передаётся по зашифрованным SSH-соединениям непосредственно в stdin Python на Telegram VPS. Запрос `logOut` выполняется на облачном API оттуда, потому что основной VPS может не иметь доступа к Telegram. При подтверждённом успехе изменяются только три параметра `.env`, пересоздаётся backend и проверяются healthcheck, доступ к NFS и наличие маркеров `TELEGRAM_CONNECTED` / `TELEGRAM_POLLING_STARTED` в логах текущего запуска. После этого вручную проверьте текст и вложения в обе стороны. После успешного cloud `logOut` возврат в облако ограничен на 10 минут: https://core.telegram.org/bots/api#logout .

## Если выполнение остановилось

- Скрипт напечатает этап остановки. Не запускайте команды наугад. До cutover обычно можно исправить причину и повторить запуск.
- Если `cloud logOut` не подтверждён, в `/var/lib/uknow-deploy/logout.state` на основном VPS останется `pending`. Backend останется остановлен. Повторный запуск автоматически не вызовет logout снова. Сначала выясните реальный результат запроса. Только после независимого подтверждения успешного `logOut` администратор может изменить состояние на `confirmed` (root: `printf 'confirmed\n' > /var/lib/uknow-deploy/logout.state`) и повторить запуск. Если точно известно, что выхода не было, специалист должен проверить безопасный способ возобновления cloud-режима или повторной миграции; не удаляйте маркер без проверки. После успешного переключения маркер — `activated`.
- Если backend не увидел NFS после перезагрузки, используйте (возможна короткая остановка backend):

```bash
bash deploy.sh 192.0.2.10 198.51.100.20 --repair-mount
```

Ввод `REPAIR` разрешает пересоздание backend, только если проверка доступа к файлу не проходит. Автоматического периодического восстановления NFS пока нет. `nofail` позволяет запустить основной сервер при недоступном Telegram VPS, но доступ к вложениям может не восстановиться сам. В режиме `soft` NFS возвращает ошибки при сбоях связи; даже чтение требует обработки ошибок/проверки полноты данных на стороне приложения. Справка: https://man7.org/linux/man-pages/man5/nfs.5.html .
- Не восстанавливайте старую `.env` и cloud polling вслепую после `logOut` или подключения local API. Сначала корректно остановите/выведите бота из локального API, проверьте возможность подключения к облаку и официальную процедуру переноса: https://github.com/tdlib/telegram-bot-api#moving-a-bot-to-a-local-server . Автоматический обратный перенос не реализован.
- Проверка логов зависит от наличия маркеров текущего запуска (старые логи могли быть ротированы). Healthcheck не гарантирует доставку всех сообщений. Проверки реальной перезагрузки, сквозной отправки вложений, DNS/TLS, диска, swap и мониторинга нужно выполнять отдельно.
