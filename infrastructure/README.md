# Развёртывание UknowApp на двух VPS

Этот комплект настраивает отдельный сервер Telegram Bot API и связывает его с основным сервером UknowApp через WireGuard и NFS.

Этот комплект предназначен для старой архитектуры целевого коммита, а не для текущего Core с NATS в `test`. Для текущей ветки используйте [Bots Gateway](../docs/bots-gateway.md).

Версия комплекта: **0.1.0**. Целевой коммит UknowApp: `588dc99079f0fc7449f80f621856ac42904c8639`.

> [!WARNING]
> Установщик пока не проверен на реальных VPS. Проверены синтаксис Bash, встроенный Python и локальный сценарий с подменённым SSH. Сначала испытайте его на тестовых серверах. Сбой может оставить систему частично настроенной.

Для обычного запуска текущей ветки на одном сервере используйте [основной README](../README.md).

## Что понадобится

- Два выделенных VPS с Debian 13 amd64 и systemd.
- SSH-доступ от root к обоим серверам (пароль или ключ).
- Публичный IPv4 основного VPS, видимый со второго сервера.
- API ID и API Hash с [my.telegram.org](https://my.telegram.org/apps), токен BotFather.
- Компьютер с Linux или macOS для запуска скрипта.

Telegram VPS не должен обслуживать другие приложения и публичные порты. Сверьте отпечатки SSH-хостов; после установки рекомендуется ограничить root SSH и использовать ключи.

### Сетевые настройки

| Порт | Основной VPS | Telegram VPS |
| --- | --- | --- |
| TCP 22 | SSH | SSH |
| TCP 80/443 | Сайт | Закрыт |
| UDP 443 | HTTP/3 (необязательно) | Закрыт |
| UDP 51820 | — | WireGuard, только от основного VPS |

Порты 8081, 2049 и RPC не открывайте в интернет. DNS и основной firewall скрипт не меняет.

Домены в `frontend/Caddyfile` целевого коммита фиксированы. Для другого домена потребуется адаптация Caddyfile и установщика; DNS и HTTPS настраиваются отдельно.

### Ограничения

- Существующий репозиторий должен находиться в `/home/uknow/UknowApp` или `/home/uknowbot/UknowApp`, соответствовать целевому коммиту и не иметь изменений отслеживаемых файлов. Новые репозитории скачиваются автоматически.
- Обновление версии приложения и перенос PostgreSQL не выполняются. Существующие база и `.env` сохраняются; для новой установки используется SQLite.
- Нестандартные сети и перенос с другого локального Bot API endpoint не поддерживаются.
- При новой установке используется фиксированный digest образа Bot API. Существующий `.env` с `latest` не меняется; обновления образов и безопасности выполняются отдельно.
- Группа Docker даёт права, сопоставимые с root. Telegram Bot API работает с UID/GID 101.

## Запуск

На своём компьютере:

```bash
git clone https://github.com/r00t0verl0rd/UknowApp.git
cd UknowApp/infrastructure
bash deploy.sh 192.0.2.10 198.51.100.20
```

Замените условные IP на реальные: первый — основной VPS, второй — Telegram VPS. Адреса используются для WireGuard и firewall. Подсеть `10.77.0.0/24` фиксирована; её пересечение с существующими маршрутами проверяется.

Скрипт подключится по SSH и при необходимости запросит пароль (в том числе повторно при проверке firewall).

1. Введите `PREPARE`, чтобы подтвердить подготовку.
2. Если `.env` ещё нет, введите API ID/Hash, пароль администратора и токен бота.
3. Для остановки действующего cloud backend и переключения бота отдельно подтвердите `MIGRATE`. Убедитесь, что других polling-процессов с этим токеном нет.

Секреты не печатаются, ввод паролей скрыт. Не запускайте скрипт с `bash -x`.

## Дополнительные режимы

### Проверить существующую установку

```bash
bash deploy.sh 192.0.2.10 198.51.100.20 --check
```

Если инфраструктура уже настроена вручную, повторная установка обычно не нужна. Проверка учитывает старый файл `.nfs-test`; при отсутствии обоих тестовых файлов или нужных конфигураций остановится.

### Только подготовить инфраструктуру

```bash
bash deploy.sh 192.0.2.10 198.51.100.20 --prepare-only
```

Backend остаётся работать в cloud-режиме, `logOut` не вызывается. Для переключения повторите запуск без `--prepare-only`. Если бот уже работает в нужном local-режиме, cloud logout не повторяется.

Скрипт не перезаписывает отличающиеся существующие конфигурации. При смене IP уже настроенного VPS согласованно обновите настройки WireGuard и firewall вручную.

## Что настраивает скрипт

| Служба | Основной VPS | Telegram VPS |
| --- | --- | --- |
| Пользователь | `uknow` | `uknowbot` |
| WireGuard | `10.77.0.1/24` | `10.77.0.2/24`, UDP 51820 |
| Docker | Backend и frontend | `compose.telegram.yml` |
| Bot API | `http://10.77.0.2:8081` | Приватный IP |
| NFS | `/srv/uknow-telegram-remote` (ro) | `/srv/uknow-telegram`, NFSv4, UID/GID 101 |
| Firewall | Без изменений | Таблица `inet uknow_guard`, SSH и WireGuard |
| Автозапуск | Docker ждёт попытку NFS; `nofail` | Docker и NFS после WireGuard и firewall |

Firewall Telegram VPS при первой установке защищён таймером отката на 5 минут. После проверки нового SSH-соединения настройки закрепляются. Отдельные таблицы Docker не очищаются.

NFS доступен только основному IP на чтение с `all_squash` (101:101). Добавляются настройки systemd и fstab, исходный fstab сохраняется. Приватные ключи между серверами не копируются.

## Переключение бота и резервные копии

> [!IMPORTANT]
> Перед переключением скачайте полный ZIP из админ-панели (SQLite). Для PostgreSQL нужна отдельная резервная копия базы и файлов. Копия `.env` в `/root/uknow-backup-...` не содержит базу и медиа.

При миграции скрипт:

1. Сохраняет `.env` и останавливает cloud backend.
2. Передаёт токен по зашифрованному SSH непосредственно в stdin Python на Telegram VPS. Облачный `logOut` вызывается со второго сервера, поскольку у основного может не быть доступа к Telegram.
3. После подтверждения выхода меняет три параметра `.env`, пересоздаёт backend.
4. Проверяет healthcheck, доступ к NFS и маркеры `TELEGRAM_CONNECTED` / `TELEGRAM_POLLING_STARTED` текущего запуска.

`DATABASE_URL` не меняется; `docker compose down -v` не выполняется. Работающие контейнеры и данные не удаляются, хотя backend может пересоздаваться.

После переключения вручную проверьте текст и вложения в обе стороны. После cloud `logOut` возврат в облако ограничен на 10 минут — [правила Telegram](https://core.telegram.org/bots/api#logout).

## Если что-то пошло не так

### Скрипт остановился

Посмотрите указанный этап. До переключения бота обычно можно исправить причину и повторить запуск. Не выполняйте неизвестные команды и не удаляйте существующие настройки.

### Не подтверждён cloud logOut

На основном VPS в `/var/lib/uknow-deploy/logout.state` останется `pending`, backend будет остановлен. Повторный запуск не вызовет logout автоматически.

Только после независимой проверки, что `logOut` действительно выполнен, администратор может отметить его подтверждённым от root:

```bash
printf 'confirmed\n' > /var/lib/uknow-deploy/logout.state
```

Затем повторите запуск. Если выхода точно не было, специалист должен проверить безопасный способ возврата в cloud или повторной миграции. Не удаляйте маркер наугад. После успешного переключения состояние — `activated`.

### Backend потерял доступ к NFS

```bash
bash deploy.sh 192.0.2.10 198.51.100.20 --repair-mount
```

Ввод `REPAIR` разрешает пересоздание backend только при неуспешной проверке файла; возможен короткий перерыв.

Автоматического периодического восстановления NFS пока нет. `nofail` позволяет основному серверу стартовать без Telegram VPS, но доступ к вложениям может не восстановиться автоматически. Режим `soft` возвращает ошибки при сбоях связи; чтение требует проверки ошибок и полноты данных. [Справка NFS](https://man7.org/linux/man-pages/man5/nfs.5.html).

### Нужно вернуться в cloud

Автоматический обратный перенос не реализован. Не восстанавливайте старую `.env` и polling вслепую после `logOut`. Сначала правильно завершите работу локального Bot API и проверьте возможность подключения к облаку по [официальной процедуре Telegram](https://github.com/tdlib/telegram-bot-api#moving-a-bot-to-a-local-server).

## Что проверить после установки

- Реальную перезагрузку обоих VPS и доступность NFS.
- Вход в приложение, передачу сообщений и вложений в обе стороны.
- DNS и HTTPS, свободный диск, swap и мониторинг.

Healthcheck не гарантирует доставку сообщений. Проверка логов зависит от наличия маркеров текущего запуска; старые логи могли быть ротированы.
